Linea has two operational halves: a control plane that accepts and observes
work, and an execution plane that performs it. They communicate through
versioned contracts, durable records, and queues—not direct application
imports.

## Product model

An Application is a customer product within a Workspace. It owns Workflow definitions and has exactly two Environments: Development and Production. Each Environment owns its credentials, identity trust, Connections, secrets, and deployments. A deployment selects an exact published Workflow version and immutable Contract revision. Executions capture that version and Environment when they start; later publication or promotion cannot rewrite an in-flight run.

| Concept                       | Why it matters                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| External Subject              | Linea's identity for an End User, separate from workspace members                                      |
| Conversation                  | One independent thread for a subject in an Environment and Workflow; histories do not merge by subject |
| Approval Request and Decision | A durable pause and one immutable human or timeout response                                            |
| Evaluator and Regression      | In-run measurement versus saved-case replay of known inputs                                            |
| Finding, Flag, and Signal     | A judgment, an alertable issue, and a recurring pattern over time                                      |

An Execution records its environment and selected Workflow version; the
Workflow itself is not permanently labeled draft, development, or production.
The same published Workflow can serve different traffic at different times.

A request moves through four layers. PostgreSQL remains the source of truth;
state crosses process boundaries through durable records, not application
imports.

1. **Product surfaces** author workflows and inspect their state: the web app
   and client applications.
2. **Control plane** applies identity, policy, contracts, and orchestration:
   the platform API, authentication, and authorization.
3. **Delivery and execution** move durable work to purpose-built processes:
   BullMQ, the execution worker, and the background worker.
4. **Runtime capabilities** resolve nodes and call external systems: the node
   registry, AI providers, and the connector gateway.

## Architectural boundaries

Every service owns one runtime concern. They share contracts through durable
records and queues, not by importing one another.

| Service           | Owns                                                | Does not own              |
| ----------------- | --------------------------------------------------- | ------------------------- |
| Web app           | Workflow authoring and operational UI               | Credentials and execution |
| Platform API      | HTTP contracts, identity, policy, and orchestration | Long-running execution    |
| Execution worker  | Graph execution and checkpoint recovery             | Public HTTP contracts     |
| Background worker | Schedules and asynchronous maintenance              | Interactive execution     |
| Mobile app        | Workspace-member monitoring and approvals           | End-User identity         |

The public contract lives outside those services, in the
[open packages](./repository-map.mdx): the protocol owns schemas, operations,
events, and stable errors, and the SDKs are clients of it.

### State and trust boundaries

PostgreSQL owns durable execution, conversation, approval, and outbox state.
Redis and BullMQ deliver jobs; a queued message alone is not the authority for
whether work exists or has completed. Operator backends use scoped Workspace
or Environment Keys; End-User clients use proof-bound End-User Sessions. The
first-party web and mobile apps authenticate workspace members. Credentials
must not cross those planes. See [trust boundaries](../security/trust-boundaries.mdx)
for the full model.

The Connector Gateway executes provider calls with stored credentials. The
sandbox-facing Run Gateway is a separate planned boundary; isolated sandbox
traffic is not yet available.

## Design principles

### Contracts have one owner

Public transport shapes live in `@linealabs/protocol`. The API and the SDKs adapt
them but do not redefine them.

### Executions bind to immutable workflow versions

An execution selects one published workflow version when it starts. Later
publishing cannot change an in-flight execution or rewrite its history.

### Execution history is a product surface

Steps retain enough structure for traces, replay, evaluation, cost accounting,
and debugging. They are not disposable worker logs.
