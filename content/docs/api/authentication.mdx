Linea uses distinct credentials because an Operator backend, an Operator
application, and an End User do not have interchangeable authority.

## Credential selection

| Caller                          | Credential                   | Scope                                                  |
| ------------------------------- | ---------------------------- | ------------------------------------------------------ |
| Operator control plane          | Authenticated member session | Workspace role and membership                          |
| Operator server integration     | Workspace key                | Explicit workspace operations                          |
| Application Environment backend | Environment key              | One Environment and its runtime resources              |
| End-user browser or mobile app  | End-User Session             | One subject, Environment, audience, and short lifetime |

Environment keys cannot change identity trust configuration or cross into
another Environment. Workspace keys cannot impersonate End Users. An
End-User Session is a short-lived capability, not a Linea account session.

## End-user authorization

The Environment key plays no part in this flow and must never be used for it.
The end user's own browser or app runs it, so no Operator backend can mint or
see the session. Running it from a server defeats that boundary.

<Steps>

### Begin authorization

The client calls `POST /v1/user-sessions/authorization` with the `environmentId`,
a `redirectUri`, and a PKCE `codeChallenge`. It then redirects the user to the
returned `authorizationUrl` at the identity provider.

### Verify identity

Linea validates the configured issuer and binds the external identity to the
canonical subject within the workspace.

### Exchange the authorization result

The identity provider redirects back with a `code` and `state`. The client calls
`POST /v1/user-sessions/exchange` with them and its PKCE `codeVerifier`, and
receives a short-lived `exchangeToken`.

### Create the session and prove possession

The client calls `POST /v1/user-sessions` with the `exchangeToken` and a DPoP
proof, and receives an opaque End-User Session. DPoP binds each later request to the client key,
method, and target URL, so copying the session value alone is insufficient.

</Steps>

A session expires 15 minutes after it is created. There is no refresh: run the
authorization again. Signing out at the identity provider stops new exchanges,
but a session already issued stays valid until it expires or is revoked in
Linea.

See [trust boundaries](../security/trust-boundaries.mdx) for the full identity
and credential map.
